# RiskPulse AI Demo Guide

## Demo objective

This demo tells the story of an underwriting team reviewing risk, pricing, and leakage exposure in one workflow. It shows how the repository turns synthetic policy data into explainable underwriting signals without claiming autonomous underwriting or production deployment.

This is a 5–7 minute walkthrough built from the actual implemented project: a React + TypeScript dashboard, a policy detail workspace, a deterministic shared underwriting engine, and a What-If simulator that reuses the same risk, pricing, leakage, and decision logic used by the backend.

---

## 1. Business problem

### What to explain

The business challenge in the demo is not a generic AI story. It is a clear underwriting problem:

- rating leakage occurs when the current premium is materially below the risk-based recommended premium
- risk-based pricing pressure appears when claims, mileage, telematics risk, and other exposures increase faster than the current premium reflects
- underwriters need explainable decision support to see why a policy is approved, reviewed, or escalated

### Why the repo matters

The implemented system combines four deterministic layers from the shared package:

- risk scoring
- pricing recommendation
- rating leakage detection
- underwriting recommendation

These outputs are then exposed through the backend API and visualized in the frontend. The resulting workflow helps an underwriter review evidence faster while keeping final authority with the human reviewer.

### Speaker notes

“RiskPulse AI is a deterministic underwriting support demo. The problem is not that the team is missing a model; it is that risk signals are fragmented. We show where current premiums are out of line with expected risk, where leakage exists, and where a human underwriter should review before approving or escalating a renewal.”

## 5. What-If Simulator

### Screen to open

Scroll lower in the same Policy Detail Workspace to the What-if risk & pricing simulator.

### What to demonstrate

Adjust the scenario inputs:

- annual mileage
- claim count
- driving behaviour risk

Then explain the resulting impact on:

- risk score
- premium recommendation
- leakage amount
- underwriting decision

This simulator reuses the same shared business logic as the backend. It does not duplicate pricing rules in a separate UI-only implementation.

### Example scenario path

Start from an approved low-risk profile and move the inputs upward. For example, a low-risk policy such as POL-2001 is a strong baseline:

- current premium: ₹1,280
- risk score: 33.6
- risk level: LOW
- leakage: NONE
- decision: APPROVE

If you increase mileage, claims count, and driving risk, the simulator shows the score and premium shifting upward. The logic calculates a new scenario record, then reevaluates risk, pricing, leakage, and decision using the actual risk engine.

### Actual policy example to reference during the demo

The repository includes a medium-risk scenario example where the policy is still actionable but flagged for review:

- POL-2009 — Imogen Wright
- risk score: 54.4
- risk level: MEDIUM
- current premium: ₹1,505
- recommended premium: ₹1,775.90
- premium change: +18%
- leakage severity: MEDIUM
- leakage amount: ₹270.90
- underwriting decision: REVIEW

This provides a very good “before/after” demonstration in the simulator without requiring fictional data.

### Speaker notes

“The point of the simulator is not to create a new pricing engine. It is to show how the same underwritten logic reacts when one or more risk inputs worsen. A small increase in mileage or claims count does not just move the premium; it can also change leakage severity and the final underwriting recommendation.”

### Why this matters

This makes the story visible to a human reviewer:

- Risk increases
- premium recommendation changes
- leakage may become material
- approval may shift to review or referral

## 7. Exact demo sequence (5–7 minutes)

### Demo flow

1. Open the dashboard (30–45 seconds)
   - show the portfolio overview and KPI cards
   - point to the review queue and leakage exposure

2. Highlight the portfolio story (45–60 seconds)
   - explain risk distribution, review pressure, and leakage concentration
   - call out actual values such as ₹16,130 total premium and 6 review policies

3. Select a policy for drill-down (45–60 seconds)
   - pick POL-2002 from the review table
   - open the Policy Detail Workspace

4. Walk through policy-level evidence (1–1.5 minutes)
   - risk score and risk drivers
   - current vs recommended premium
   - leakage card
   - underwriting decision card

5. Show the AI Underwriter Brief (45–60 seconds)
   - explain the summary, evidence, and decision support framing
   - emphasize the disclaimer that the human underwriter remains final authority

6. Demonstrate the What-If Simulator (1–1.5 minutes)
   - adjust mileage, claim count, and driving risk
   - explain how risk, premium, leakage, and decision shift together
   - point to the risk-score movement and recommendation change

7. Close with business value and next step (30–45 seconds)
   - summarize why this helps underwriters act faster and more consistently
   - state clearly that the app is a deterministic decision-support prototype built from synthetic data

Estimated total: 5–7 minutes

## 8. Backup flow if an API or runtime issue occurs

If the app does not load or the backend is unavailable, do not improvise a different product story. Use the repo’s deterministic logic and synthetic dataset as the fallback narrative.

### Backup path

1. State that the app is built on a deterministic underwriting model with synthetic data.
2. Explain the data flow from the backend endpoints:
   - /api/dashboard-summary
   - /api/policies/:policyId
   - /api/policies/:policyId/risk-profile
   - /api/policies/:policyId/pricing
   - /api/policies/:policyId/leakage
   - /api/policies/:policyId/underwriting-decision
   - /api/policies/:policyId/ai-brief
3. Use known actual outputs from the synthetic dataset as the fallback examples:
   - POL-2001: APPROVE, LOW risk, no leakage
   - POL-2002: REFER, CRITICAL risk, critical leakage
   - POL-2009: REVIEW, MEDIUM risk, medium leakage
4. Explain that the same logic is used in the frontend simulator, so the story remains consistent even if the UI is temporarily unavailable.

This keeps the demo grounded in the implemented repository rather than in fictional product claims.

## 9. How GitHub Copilot was used

GitHub Copilot was used as a supporting engineering assistant in the repository, not as an autonomous decision-maker for underwriting logic or product claims.

Based on the project documentation and the repository itself, Copilot was used to help with:

- monorepo and workspace setup
- TypeScript and app structure
- shared policy data model and synthetic inputs
- deterministic risk score, pricing, leakage, and underwriting engine implementation
- backend API contracts and route logic
- dashboard and policy detail workspace implementation
- What-If Simulator logic and INR formatting
- test coverage and documentation updates

This was done in a staged, incremental workflow rather than a single giant generation step. The repository guidance in `.github/copilot-instructions.md` and the development notes in `docs/copilot-development.md` kept the work aligned with:

- insurance underwriting decision support
- synthetic-only data
- explainability and human review
- frontend consistency and UI design requirements
- validation with build and test commands

The outcome is a deterministic, explainable demo application grounded in the actual repository and the synthetic dataset, not an imaginary production AI underwriting platform.
